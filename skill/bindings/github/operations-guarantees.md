# What each GitHub binding operation guarantees

The operations table in [`skill/bindings/github.md`](../github.md) names every operation; this
document carries what each one guarantees beyond the obvious. The tool's schema carries its arguments.

| Operation | What it guarantees beyond the obvious |
|---|---|
| `ensure_states` | idempotent; run it before your first write to an unfamiliar project |
| `flush` | sends the writes queued while the git operation window was closed, oldest first, each read back before the next; refuses while the window is closed and `outbox-pending` when a write stops it. `--read-only` lists the queue and sends nothing |
| `create` | creates every label **before** attaching it, then projects the initial state onto every project the issue belongs to — the case everyone forgets, because no `transition` ever follows a fresh issue to correct an empty `Status`. The identity and any `--blocked-until` clauses are recorded in the local store in the same transaction that admits the issue, and no `analysis` or `blocked-until` marker is written to the body: a body with no `--epoch` reaches `gh` as the caller wrote it, and a `--blocked-until` is refused unless the filing is `--state blocked` (`invalid-blocked-clause`). A filing whose store record cannot be written is a write failure naming the issue that was filed, and repeating the same `create` (same identity and title) adopts that issue instead of filing another. `--epoch` names the publication a finding was recorded against and is recorded in the store as a `review` marker, never rendered into the body; `--findings` names one or more `+`-separated finding identities and is refused without `--epoch`. The answer carries `priority_checked`: true only when the priority's scale is the routed domain's declared scale **and the label after the colon is non-empty** — filing is never refused for it, and the queue read names what was not checked, though only on a scale the transport can read (today just `general`'s `priority`); a filing on a domain whose scale it cannot read is answered `false` and is not named |
| `list_state` with `identities` | read-only, no claim required and no `run_id`. The dedup key each **open** issue recorded when it was filed — the `identity` field `create` records and `domain-composition.md` calls the one on which equivalent findings collide — answered as `{number, identity}` per issue, never read from the title. The key is the local store's `issues.identity`, which `create` recorded, or the lazy import read from an `analysis` marker an older body still carries: the open issues are one REST list read and no per-issue read is paid. An issue that recorded no identity, or one the store has never admitted, answers `identity: null`, never `""`, so a caller can tell *no key* from *an empty one*. `--limit` defaults to 200 and is a ceiling, reported by `at_limit`; a cut holds the oldest issues |
| `list_state` | the unassigned issues the **local store** puts in state `<s>`, intersected with the open-issue list from the REST issues endpoint (`gh api --paginate --slurp repos/{owner}/{repo}/issues?state=open&per_page=100&sort=created&direction=asc`), not `gh issue list`, which routes any `--label` through GitHub's lagging search index. No label filters the list: a `status:` label never decides, the store does, and an open issue the store has never admitted is reported under `unadmitted`. The request names ascending creation order, so a cut holds the **oldest** open issues; pull requests are dropped and the answer is cut to `--limit 200`, which `at_limit` reports. The cut preserves oldest-first selection, not ranking. The holder is the store's ownership fold, never a GitHub assignee: an issue with a live holder is dropped, and `open` reports how many the state holds. For `review`, it reads each candidate's timeline and eligibility from the store, excludes unresolved handoffs from their publishing/requesting run with receipt, blocker, discharger and deadline, and leaves another run eligible. For `blocked`, it reads each item's `blocked-until` clauses from the store and answers `conditions`, each with `holds`, beside `dischargeable`; a clause that is not well formed or names an issue the store never admitted is `holds: false` with `unparsed`/`unread`, never dropped. Results are partitioned by `domain:<name>` and never ranked across partitions. Items with no value on a readable partition scale are named under `unchecked`, absent when there are none |
| `claim` | records the claim in the local store and posts no comment; the assignee and the `dev:<runtime>` label follow as a projection. `--transition-to` runs the paired `transition` in the same call, claim first; omitting it claims without moving. The retry rule and which refusal it meets are in *Claim* in github/operations.md |
| `reclaim` | target discovery is read-only; the write binds target, evidence, privilege and metadata, records the takeover in the local store with no comment on GitHub, then proves exact projections. It refuses the publishing/requesting run of an unresolved review handoff on the same terms as `claim`, so a replacement that went stale cannot return the item to the one run forbidden to review it. When nobody holds the issue live and the only expired acquisition on it is this run's own it refuses `stale-self-requires-claim` rather than displacing itself — a takeover of nobody is not the operation this is — and its answer says to call `claim` instead, which now accepts exactly that case. A live foreign holder takes priority as the target even so: the same call against that holder, unforced, refuses `holder-not-stale` instead, whether or not this run also has a stale acquisition of its own sitting alongside it. A takeover that lands and the ownership fold then refuses — an epoch the re-read no longer carries or no longer holds, or a live holder taken without `--force` — answers `reclaim-discarded` carrying the `condition` that dropped it and, when a holder remains, the run that still holds the issue — the no-holder shape, a target that scrolled out of the fetched window while the takeover displaced nobody, omits `winner` because the timeline shows no holder to name; that is not a race this run lost, and only a takeover that counted and is still held by somebody else answers `lost-reclaim-race`. The conditions a fresh `reclaim` cannot carry: `comment-untrusted`, `comment-edited`, `marker-malformed` and `reserved-elsewhere` are reader-level, `evidence-unproven` cannot fail when the command hashes its own evidence, `target-run-mismatch` cannot when the command writes `from` from the epoch it names, and `legacy-takeover` is fold-internal with no operation id to address; a write meeting one meets an earlier conflict or a write failure instead |
| `verify_claim` | proves the requested run is the reducer's current live winner, over the local store (an issue is imported from GitHub on first touch; afterwards GitHub is asked one REST question, whether the issue is open), and uses timeline position, not second-precision timestamps, as its control-message watermark. A closed-issue exception reads every page of closing PRs and matches this run's review transaction, the closing PR, and a merge whose second parent is exactly that receipt's head and whose first parent descends from that receipt's base, and answers `closed-by-own-delivery` with the delivering SHA and epoch. `--allow-closed-by-pr` pins that PR. Any other close is still `issue-not-open`. Incomplete or malformed pagination is a failed read |
| `transition` | projects the state onto every project the issue belongs to **first**, swaps the label in **one** call, then reads **both** back and repairs a project that disagrees. Omitting `--from` removes whatever stale state labels it finds; `--from` naming the same state as `--to` removes nothing, so asserting the state an item already holds is safe. A read-back that disagrees is refused **as a write that landed**, and the refusal names the repair: the same transition with `--from` omitted |
| `comment` | file-based body, always; `--run-id` and `--kind` are a pair, validated and deciding no text. The comment is the caller's prose alone — no marker is appended — and three shapes in it are escaped so it cannot become a control event for an older reader, fall through to the prose parser, or swallow a marker that follows it: a quoted issue-flow marker, claim-shaped legacy prose, and a comment opener that does not close within the text itself |
| `blocked_until` | local to the store: **no GitHub write**. Records one clause that holds when the local store puts issue `<m>` in state `<s>`, which `list_state --state blocked` evaluates exactly as it does a clause imported from an older body; recording the same clause twice records it once (`recorded: false`), and `--clear` removes every clause of the issue (`cleared: <count>`). No claim is required, because an analyst files a blocked issue without holding one; the issue must be one the store holds in `blocked` (`issue-not-blocked`), and a clause needs both a positive issue number and a workflow state (`invalid-blocked-clause`) |
| `task` | records or revises one row of the claimed issue's ODD checklist in the local store: **no GitHub write**, and the live claim is verified first exactly as `verify_claim` does, against `--expect-state` (default `in-progress`). A task id the store has not seen needs its `--text` and `--route` (`task-incomplete`); a revision names only what changes and keeps the row's place; `--status done` needs a `--commit` recorded now or before (`task-done-without-commit`). The id is 1 to 40 of letters, digits, `.`, `_` or `-`, the commit 7 to 64 lowercase hex digits (`invalid-task`). The answer carries the whole checklist as `tasks` |
| `tasks` | read-only, no claim required and no `run_id`: the issue's checklist in the order its tasks were first recorded, as `{id, text, route, done, commit}`. A resume reads this before it holds anything |
| `heartbeat` | renewal first, record second; **refuses to record** when the renewal says stop, posts no comment (the note and the marker live in the local store; the answer says `recorded`), escapes control-shaped text before appending its own marker — a `heartbeat`, `progress` or `blocked` marker, as `--kind` names — and refuses any other kind before it reads anything (`renewal-kind-unsupported`), since `branch` and `published` have writers of their own |
| branch + worktree | renews first, records the `branch` marker in the local store with no comment on GitHub, then serializes on a branch-scoped lock and reserves the whole local checkout **before any GitHub mutation**, so a lost reservation leaves no remote state. Resumes only a checkout whose durable ownership marker names this run; a template missing `<branch>` or `<run-id>` gains that scope as an in-memory sibling, without rewriting `estigia.local.md`. Resolved paths retain native POSIX spelling on Linux and macOS, while Windows' `\\?\` prefix is removed before invoking Git because Git for Windows rejects its slash-normalised `//?/` form. It fetches the named base before recording or branching from its remote-tracking ref. Ref existence is probed so absence and a failed read are different answers, a nonzero or timed-out `gh issue develop` is re-read rather than believed, and the isolated worktree head, published head and recorded remote base must agree before success is reported; the caller's main checkout may diverge without being mistaken for the new branch. It records the base COMMIT and the base TREE, so a later movement check compares against what the base contained rather than resolving it again. The local worktree registry is read NUL-delimited and fails closed: a failed, truncated or contradictory read is a failed read, never an empty registry |
| `judge_workspaces` | mints one **bare working directory** per Judgment Day judge for a panel over the named receipt, resolved from `Worktree location` the way `start-branch` resolves the claimed checkout, so the directories are its siblings and are scoped to the run and the head. It creates each directory and reads it back before answering; a call that cannot make one per judge refuses `judge-workspaces-uncreatable`, naming the count asked and the count creatable, and removes what it made rather than returning a short list. A count above 64 refuses `judge-workspaces-count-too-large` before anything is resolved. A resolved directory inside the checkout the claim covers refuses `judge-workspaces-inside-the-claimed-checkout` before anything is created. The directories are bare, not checkouts of the reviewed head: a `reading` judge has nothing to build and a `measuring` judge gains no tree the repository did not configure. It hands out directories and proves nothing about where a judge wrote |
| `publish_review` | `--expected-epoch` is the epoch of the newest publication on the branch's own pull request as the answer you are acting on read it, or `none` for a branch with none; any other newest publication refuses `expected-epoch-moved` before anything is pushed, so a stale instruction is never executed — see *Publishing a review target* in github/operations.md |
| `republish_review` | the same operation as `publish_review` in everything but the push (`--expected-epoch` and `--with-review` included) (`--expected-epoch` included, checked before the lease renewal), for a branch whose history was rewritten — rebased onto a moved base, or amended, where the ordinary push is refused as a non-fast-forward. It reads the **newest `published` marker on the branch's own pull request** and pushes `--force-with-lease=<branch>:<that head>`, so the remote is required to still be at the bytes a receipt bound; a remote that moved since refuses the push and nothing is destroyed. The live claim is verified a second time immediately before the push, after the fetch, target derivation, keyword scan, PR listing and draft conversion that separate it from the first. An issue with no recorded publication is refused `published-transaction-missing`: the first publication is `publish_review`'s. There is no plain `--force` and no way to reach this from `publish_review`. It starts the same publication lane set, on the same terms. `--topology`/`--topology-reason` are read and refuse identically — the topology refusal sits before the lease renewal too, so a rewritten history whose changed-file count crosses the threshold cannot force-push past it silently either. It refuses `publication-base-not-ancestor` on the same terms too, before either the correction budget check or the lease renewal, so a rebased history whose new base still is not an ancestor of its head cannot force-push past that either. The correction budget check runs identically here too, before the lease renewal, so a rewritten history cannot force-push past a spent budget or outside its genesis paths either |
| `handoff_review` | one ordered operation: verifies the live `review` claim; validates the newest full receipt on its own pull request and exact ownership epoch; records and reads back an immutable `review-handoff` carrying authority `auto`, an internally generated request time and a deadline equal to it, so nothing elapses on it; invokes the existing idempotent exact-target `unassign`; then confirms the released epoch is no longer authoritative and state remains exactly `review`. Only after this success does the MCP pointer clear |
| `review_finding` | see *Recording a finding* in github/operations.md |
| `escalate_review` | records a local `escalated` receipt, and only while `review_status` answers `corrections.correction_spent`; the condition, the `escalate-review-already-approved` refusal and why it does not release CI are in *Escalating a review* in github/operations.md |
| lens report, refutation and validator result records | written only by `collect_review_input`; a call by hand is refused `recorded-by-capture-only` and writes nothing — see *Recording a lens report*, *Recording a refutation* and *Recording a validator result* in github/operations.md |
| `review_disposition` | see *Recording a disposition* in github/operations.md |
| `launch_review_input` | requires a live claim in `review` by the launching run, verified before each job starts; records nothing — see *Capturing a review input* in github/operations.md |
| `collect_review_input` | requires a live claim in `review` by the run that launched the job, verified again by every write; records the answer of the job `launch_review_input` started, once, or refuses without writing — see *Capturing a review input* in github/operations.md |
| `review_computed_verdict` | see *Recording a computed verdict* in github/operations.md |
| `review_read` with `view: verdict` | read-only, no claim required. The outcome, open and escalated finding ids, follow-ups and unreported lens roles one exact receipt computes, recording nothing — see *Recording a computed verdict* in github/operations.md |
| `record_spend` | requires a live claim in `review` by the recording run. Records one measurement of what a phase cost against a review transaction — recorded, not verified, the same standing as a finding's `evidence`. Unlike `review_finding`, the receipt need not be this issue's current one: a round's cost stays recordable once a later `republish_review` supersedes it, checked only against every receipt this issue's timeline ever published rather than the latest. `--input` is bytes the phase was handed (brief plus payload) and `--tokens` is what it consumed; the two are kept apart on purpose and nothing here divides one by the other. `--conditions` names what this measurement varied and is part of the operation's identity alongside the receipt and `--phase`: two records naming the same receipt and phase but different conditions are two measurements, not a replay of one. `--input`, `--tokens`, `--seconds` and `--contexts` must each be a positive integer, refused as `non-positive-spend-value` otherwise. `--phase` outside its four-word vocabulary is refused as `invalid-spend-phase`, and a blank `--conditions` is refused as `blank-spend-conditions`. The immutable marker is operation-idempotent |
| `review_read` with `view: spend` | read-only, no claim required. Every recorded measurement of the named phase, each carrying its own receipt and `conditions`, so the same layer measured twice can be set side by side — this is the primary answer. `issue_totals` sums every phase and every receipt this issue ever recorded spend against, broken down by phase and by epoch, useful for spotting rounds; it is not the comparison, and nothing here divides one figure by another to make it look like one |
| `review_status`, its `corrections` | read-only, no claim required. Answers where the change under review stands against **`Corrections per lineage` corrections per lineage** (default 3). A lineage is an original candidate and its repairs on one pull request; **everything is counted only for the pull request the issue's latest publication names** — an issue outlives its changes, and a delivered one's history is not the next one's. `rejections` is every publication on that pull request whose receipt stands rejected or escalated: a computed `rejected` or `escalated` verdict, a retired `review-verdict` `rejected`, or a local `escalated` receipt, the latest computed marker deciding and an `incomplete` one deciding nothing. `corrections` is how many corrections the current lineage has spent, derived from the `parent` receipts `published` markers carry and never stored: a `published` marker whose parent **on the same pull request** stands rejected or escalated is a correction; one whose parent no panel has judged is neither, since republishing before any panel recorded anything corrects nothing; one whose parent stands `approved`, a first publication, and one whose parent is on a different pull request each begin a new lineage and zero the count. `correction_limit` is the resolved `Corrections per lineage`; `correction_spent` is `corrections` at the limit; `correction_available` is the newest publication standing rejected or escalated with the limit not reached; `latest_verdict` is that newest publication's standing, `approved`, `rejected` or `unjudged`. Decides nothing itself — the refusal of one past the limit is `publish_review`'s, and the escalation the answer feeds stays the orchestrator's own read of it |
| `review_status` | read-only, no claim required. The one next step of the review, from the local store and the pull request, never a comment or label read: `execute` (a tool and its exact arguments, bound to the receipt or to `expected_epoch`), `collect` (inputs, each with its capturing tool) or `stop` (a coded reason). An unreadable store, pull request or lane is an `unavailable` refusal. A command it named is refused `stale` when the receipt moved after the answer (`published-transaction-mismatch`, `expected-epoch-moved`): read again, never retry the old answer |
| `review_read` with `view: findings` | read-only, no claim required and no `run_id`, for a refuter adjudicating findings it was handed rather than performing this repository's own re-review. `--epoch` resolves to a **full receipt read off the timeline**, never to caller-supplied bytes: a publication this issue's timeline actually recorded, or — failing that — the latest publication's own recorded lineage parent, so a parent whose own `published` comment was deleted is still answerable; omitting `--epoch` answers the latest publication. Findings are matched against that resolved receipt, never by a finding's own `epoch` field — that field is whatever the finding says it is, and selecting the publication first is the safe direction. `selected` is `latest` or `epoch`; `parent_epoch` names the resolved receipt's own recorded parent when it has one. Structured fields only by default, plus `blocking` (from `is_severe()`) and `evidence_bytes`/`impact_bytes`; `--with-text` adds `evidence` and `impact` verbatim, refused rather than truncated past `FINDING_TEXT_CEILING` (32768 bytes, summed over the findings being answered) — read the same receipt without `--with-text` first, then one finding at a time with `--id`. An issue with no complete publication at all refuses `published-transaction-missing`; an empty ledger answers `ok: true` with `findings: []` |
| `review_read` with `view: transaction` | read-only, no claim required and no `run_id`. The recorded publication for one epoch — everything `publish_review`/`republish_review` no longer carry in their own answer: `topology`/`topology_reason`, the lineage (`parent`/`parent_pr`/`parent_head`/`parent_base`/`parent_digest`/`delta`/`delta_range`/`delta_range_reason`), the publication lane's `publication_lane_note`/`publication_lane_workflows`/`publication_lane_count`, the `autoclose` verdict, its `mandatory_follow_up` and `autoclose_assessed` (`false` on a marker written before the verdict was recorded, whose `will_autoclose` is then `null` rather than a false "no"), plus the identity fields (`epoch`, `pr`, `head`, `base`, `digest`, `url`, `confirmed`), exactly as the marker recorded them. `--epoch` names an epoch this issue's own timeline recorded, or omit it to answer the latest publication; unlike the `findings` view there is no fallback to a latest publication's recorded lineage parent, because an epoch that exists only in that parent field has no marker of its own to answer from. A well-formed epoch the timeline never recorded refuses `publication-epoch-not-found`, naming every selectable epoch; a malformed one never reaches that search — it is refused first by the same operation-id check every named epoch passes. An issue with no complete publication at all refuses `published-transaction-missing`. |
| `review_read` with `view: membership` | read-only, no claim, no `run_id`. Whether a candidate reviewer-facing text — a **path**, never inline, since a payload can run past a shell's own command line — is a genuine subset of the payload one exact receipt named. The receipt resolves as the `findings` view's does, never through `recorded_receipt`: the named `--epoch`, its latest publication's recorded lineage parent, or the latest publication when `--epoch` is omitted. `--candidate`'s payload is recomputed from that receipt's `base`/`head` with the call `publish_review` made, run isolated the same way, and the recomputed digest is reconciled against the marker's own `payload-digest` **before** anything about `--candidate` is asked; a disagreement answers `payload-rebuild-mismatch` with **no line reported** (see `payload-rebuild-mismatch` in `github/refusals.md` for what can still move it). A receipt with no recorded `payload-digest` — before the field existed, or reached only through an inherited lineage parent with no marker of its own — answers `payload-digest-unavailable` rather than crossing against nothing. Only once digests agree is `--candidate` tested, and only for membership: every non-empty line must be a line somewhere in the payload, never the reverse, so withholding whole files for a sealed reviewer's limit stays legitimate. The first line that is not answers `payload-line-not-found`, naming its 1-based position; a passing answer carries `omitted`, the payload's own distinct non-empty lines absent from `--candidate`, so a caller can state its subset honestly. Membership checks presence only — never order, multiplicity or which file a line came from — so a candidate assembled entirely from real lines can still misrepresent the change and answer `ok: true` |
| `review_read` with `view: inspect` | read-only, no claim, no `run_id`. The correction one recorded publication made over its parent, for a validator with no checkout: between that publication's `head` and its recorded lineage parent's `head`, never caller-supplied commits. `--path` (and `--side` for `object`) can only name a path the correction changed. Answers `{ok, issue, epoch, request, path, side, text}`. Refuses `invalid-operation-id` for a malformed epoch, `malformed-argument` for a request, `path` or `side` that do not fit, `inspect-parent-missing` for a first publication or a recovered successor (a fresh candidate, not a correction), `publication-epoch-not-found` for an unpublished epoch, `reviewer-inspect-transaction-unresolved`, `reviewer-inspect-outside-correction`, `reviewer-inspect-absent-side`, `reviewer-inspect-unreadable` (the candidate is uninspected, not passed) and `reviewer-input-too-large`; never truncates |
| `release_ci` | verifies a live claim in `review`, requires the supplied receipt to be the newest complete publication on its own pull request, whoever published it, refuses a terminal `escalated` receipt whatever the ledger computes (`review-receipt-escalated`), requires the receipt's recomputed computed verdict to be `approved` and equal to its recorded marker, a `low` receipt needing none — see *Recording a computed verdict* in github/operations.md — re-reads the same draft PR/head/base, and re-derives one coherent clean target before `gh pr ready`. A `warning` or `suggestion` on the receipt is informational and never blocks this. Every ready outcome is read back: an exact ready target is success even when the command failed ambiguously; otherwise the read/write taxonomy is preserved |
| `review_status`, its `lane` | read-only. Answers the publication lane for that head as `green`, `red`, `never-ran`, `running`, `absent` or `disabled`. `disabled` is read mechanically and is not `absent`: `repos/<owner>/<name>/actions/permissions` reporting `enabled: false`, or every workflow under `.github/workflows/` carrying `disabled_manually`. An unreadable check-run listing, and an unreadable permissions answer, are failed reads rather than named states. `absent` keeps its meaning: no check runs, so Estigia cannot prove a lane exists. Read it before launching the lenses: red, do not launch; never-ran (its jobs all report no steps), launch — `record_computed_verdict` can still approve, gated on evidence; running, wait or launch knowing the computed verdict may not be recordable; absent, proceed; disabled, CI cannot run, so proceed and merge as *CI, merge and delivery* in github/delivery.md states for such a repository, recording the answer's `read` on the issue first; unreadable, not clearance. Nothing refuses a panel launched over a red lane — a launch is not a write the gate sees |
| `review_tier` | read-only, no claim required — see *Deriving the review tier* in github/operations.md |
| `review_tier` with `parent_head` | read-only, no claim required — see *Deriving a repair's tier* in github/operations.md |
| `target` | read-only. Emits the COMPLETE delivery target — the exact base through `HEAD` plus the uncommitted worktree — as a path/mode/blob manifest with one digest. With `--native-start` it compares a reviewer's target against it and **fails closed**, naming the paths that would ship unreviewed. `--brief` omits the `manifest` array and nothing else: the digest and the `--native-start` comparison are both taken from the internal target, so neither moves between the two shapes. Uses `ls-tree`, `--no-optional-locks status` and `hash-object` without `-w`, so no object is written and the index, worktree and refs are untouched — it is safe to run against a tree somebody is still working in |
| `target` with `recorded_base` | read-only. Classifies later base movement as none, compatible, overlapping, conflicting or unknown, from exact refs, changed paths and `git merge-tree --write-tree` (git 2.38+; below that the answer is `unknown`), which touches no index, worktree or branch — it does fetch, and does write the merged tree into the object store, so it changes nothing about the delivery but is not literally write-free. Unknown is never compatible, and semantic impact is reported as the caller's judgement rather than decided. The answer's `integrate` is the movement's own reading, not this repository's route: under `required_status_checks.strict: true` every movement but `none` still forces an integrating republish, which the contract makes a repair-shaped round over the parent receipt on `compatible` and a whole-change re-review on every other value |
| `changelog-notes` | reads the changelog; **`--out` writes that file**. Extracts the version's entry for its tag and Release, anchored on the version **opening** the heading. Fails closed on a missing or empty entry — a tag is immutable, so notes invented at tag time are permanent |
| `check closing keywords` | run again before merging: the branch's commit messages can introduce one after the body is already clean. Historical merged closers and open PRs for another named branch/base are excluded from the current-delivery verdict |
| `unassign` | retries cannot release a later acquisition; the release itself is recorded in the local store and posts no comment — see *Releasing an issue* in github/operations.md |
| review verdict | computed from the finding ledger and recorded by `review_computed_verdict`. The lenses record findings; the tool records only one computed outcome and exact publication identity. Use the lenses the tier licenses: a severe finding is settled by the ledger at every tier, stated in full in [blind judges](../../policies/blind-judges.md). Estigia cannot prove panel size, concurrency, independence, blindness, same-finding identity or quorum. Reject a verdict naming any earlier epoch |
| `ci_status`, `merge`, `publish_version`, `close` | performed by the agent, not scripted: see *CI, merge and delivery* in github/delivery.md for `ci_status` and `merge`, including the rule there that CI is a delivery requirement only where it can run, *Version tags* for `publish_version` and *Closing* for `close` |
| `last_activity` | only trusted `heartbeat`, `progress`, `blocked`, `branch` or `published` markers authored by the holder extend liveness beyond acquisition; mentions and control targets do not |
| assisted checkout | reads the issue first (`gh issue view`), and a failed read (`assisted-issue-unreadable`) or a closed issue (`issue-not-open`) stops before any repository write. Then the same local reservation `start-branch` makes: a branch-scoped lock, the whole checkout reserved, the ownership marker written. **Writes nothing to GitHub**: no claim, no label, no comment and no `gh issue develop` sidebar link. Offered only where the `Claim workflow` row is `assisted`, and refused everywhere else; the claim it leaves is the local run pointer alone |
| draft pull request | publishes an assisted run's branch as a **draft** and writes nothing to the tracker: no marker, no receipt, no `Refs` line, no comment, label or state. `--branch` and `--worktree` are not the caller's: the MCP tool fills them from the run pointer `assist` recorded, and a run whose pointer is not assisted is refused before the transport runs. The checkout must have that branch checked out (`git symbolic-ref HEAD`), or it refuses `draft-pr-branch-not-checked-out`. The body file is read once and written as given. A closing keyword in the title, the body or the branch's commit messages refuses `closing-keyword-live` before anything is pushed, because a merge would close the issue in Estigia's name. The base is the repository's default branch. An open pull request for the branch is looked up before the push: an open draft is reused and read back (a retry makes no second one), more than one refuses `ambiguous-open-prs`, and one that is ready for review refuses `draft-pr-exists-ready` — it is never converted or edited. The push is a fast-forward and never forced, inside the `Git operation window`. The pull request is then read back until it is open, a draft, and at the pushed head; a read-back that never agrees is `draft-pr-readback-failed` in the `committed` world — the push landed and a pull request may exist, so no pull request is reported. CI and review on the draft are the team's own and nothing waits for them. Offered only where the `Claim workflow` row is `assisted` |
