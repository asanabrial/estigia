# Refusals from the GitHub binding

These say nothing about the tracker. They say the call could not be made, so nothing was attempted
and nothing was written — retrying the same call unchanged will produce the same answer.

| `reason` | What it means | What to do |
|---|---|---|
| `unknown-operation` | The operation name is not one that exists. | Use a name from the operations table in `github.md`. |
| `missing-argument` | A required argument was not passed. The refusal names it in `argument`. | Pass it and call again. |
| `malformed-argument` | An argument was passed and could not be read as what it has to be — an issue number that is not a number. The refusal carries the `value` it was given. | Correct it and call again. |
| `blank-argument` | A required argument arrived carrying nothing. It is neither missing nor malformed, and it is refused because every one of these is taken into the world as a name: an empty `--to` writes `status:` with nothing after the colon, an empty `--run-id` claims an issue for nobody. The refusal names the flag in `argument` and in its own sentence. | Send the value and call again. |
| `incomplete-review-transaction` | A review operation did not carry a 32-hex epoch, positive PR, full lowercase head/base SHAs, or 64-hex digest. | Correct the invocation from the latest `publish_review` answer; do not shorten or reconstruct receipt fields. |
| `blank-topology` | `--topology` was passed as an empty or whitespace-only string, or as filler standing in for an answer. Read as absent it would be recorded nowhere — the marker drops empty values — while the prose still declares it. | Declare how the change was written, or omit `--topology` entirely. |
| `blank-topology-reason` | `--topology-reason` was passed as an empty or whitespace-only string, or as filler. | Say why the declared topology needed no delegation, or omit `--topology-reason` entirely. |
| `topology-reason-without-topology` | `--topology-reason` was passed with no `--topology`. A reason explains a declaration; on its own it is kept on the marker but dropped from the prose and from `publish_review`'s own answer, so the surfaces disagree. | Declare `--topology` alongside the reason, or omit `--topology-reason`. |
| `publication-comment-too-large` | The caller's own fields — `--run-id`, `--topology` and `--topology-reason` — would render past GitHub's 65,536-character comment cap once the rest of the published record is counted. Nothing is posted to GitHub any more, so the cap no longer bounds a write; the refusal remains as a conservative limit on the record. The topology is rendered twice — percent-encoded on the marker and escaped in the prose beside it — and `run_id` once; none is bounded by a constant, and `run_id` is **not** bounded by the run-pointer filename, since `session::store` is best-effort. The budget also reserves the frozen genesis manifest's own ceiling and the publication lane's own measured width, so a manifest at its limit, a lane as wide as the repository's workflows and the caller's text at this one still fit together. Nothing was pushed and no pull request was touched. | Shorten the run-id, the topology or its reason. |
| `review-handoff-operation-conflict` / `review-finding-operation-conflict` | One deterministic operation ID is already bound to different or incomplete immutable marker fields. | Do not edit protocol comments. Re-read the timeline; unchanged retries reuse the original event, while a genuinely different event needs different immutable inputs. |
| `dirty-review-target` | Publication or CI release found uncommitted paths, which no PR head can identify. | Commit or remove them, then publish a new epoch. |
| `review-payload-too-large` | The unified-hunk payload of this publication exceeds the named byte ceiling. A truncated payload would still let a reviewer report a clean verdict over a partial view. | Split the change. Nothing was written. |
| `review-target-moved-during-read` | HEAD changed while the clean manifest was being derived. | Wait for the checkout to stop moving and derive a new target. |
| `publication-base-not-ancestor` | `--base`'s current tip is not an ancestor of the branch's head — the branch was rebased onto an earlier point and the base has since moved past it. A two-dot diff between them would carry everything the base gained in the interval inverted into what reads as this change's own deletions. Checked before the payload is materialised; the refusal carries `base`, `head` and the `merge_base` between them. Nothing was pushed and no pull request was touched. | Integrate the base's current tip into the branch from `in-progress`, as one bare command — `git -C <worktree> merge --no-edit origin/<base>`, nothing beside it. The re-review reads the whole change. Outside a correction a rebase then a new publication also clears it: `republish_review` when the issue has a recorded publication, else `publish_review`. During a correction, a receipt already standing on the branch's open pull request, only the merge is named: a rebase rewrites the parent head and the correction escalates to a person as `validator-delta-carries-upstream`. |
| `correction-budget-exceeded` | This repair's own tree-to-tree changed lines — measured against the parent publication's own candidate tree, or, when the base advanced and was integrated, against the tree git merges the parent head and the new base into — added to the cumulative every earlier accepted repair on this lineage already spent, exceed the budget frozen from the original candidate's own size. Nothing was pushed and no pull request was touched. | The remaining work is larger than this candidate's repair allowance. Publish it as a new change on a new pull request, which starts its own lineage and its own budget. |
| `genesis-manifest-too-large` | The original candidate's own frozen `budget-genesis-paths`, measured at the percent-encoded length the published marker would actually carry, exceeds `GENESIS_MANIFEST_CEILING` (32768 bytes). Nothing was pushed and no pull request was touched. | Publish this change as a new change on a new pull request, which starts its own lineage; a first publication writes no manifest at all. |
| `correction-outside-reviewed-scope` | This repair changed a path outside the frozen genesis paths — and, when the base advanced and was integrated, outside the paths that merge conflicted on and the advance's rename destinations — that is not an admissible companion test, and the refusal names the first such path. The refusal carries `genesis_paths` and `integrated_paths`, the latter empty when the round is not integrated. Nothing was pushed and no pull request was touched. | Keep the correction inside the paths that were reviewed, or add only a companion test alongside one of them (a `_test.rs` file, or anything under a `tests/`-shaped directory next to it). Otherwise it is a new change, not a correction — publish it on a new pull request, which starts its own lineage and its own budget. |
| `correction-already-spent` | This publication descends from a parent on the same pull request that stands rejected or escalated, and the lineage already spent the corrections the `Corrections per lineage` row allows (`review_status`'s `corrections` answer `correction_spent`). Nothing was pushed and no pull request was touched. The refusal carries `corrections` and `correction_limit`. | Hand the decision to a named person with `escalate_review`, which a spent correction opens, or publish the remaining work as a new change on a new pull request, which starts its own lineage and its own corrections. |
| `approved-republish-without-cause` | This publication descends from a parent on the same pull request whose latest verdict was an approval, no `review-finding` has been recorded against that exact parent receipt since that verdict, and the base has not **advanced** past the parent receipt's own recorded base — the parent's base is not a proper ancestor of this publication's, so a base that merely differs, reset backwards or swapped for another line of history, earns nothing. A republish over an approved receipt spends no correction but stays inside its pull request's correction budget and scope, and nothing gave this one a reason to be. Nothing was pushed and no pull request was touched. | Record a `review_finding` against the parent receipt naming the defect the panel did not weigh, or merge the base's advance in. A warning or suggestion the panel declined to block on is delivered and informational, not republished — the finding is preserved against its receipt either way. |
| `draft-readback-failed` | A reused PR did not read back as draft before push. | Do not push; establish why GitHub kept it ready. |
| `review-status-issue-not-in-store` / `review-status-store-unreadable` | The store-only timeline read `status` stands on found no record of the issue, or could not read the store (absent schema, another schema, not a database). Unavailable class: nothing is known, and an absent record is never an empty timeline. Reads no GitHub. | Claim the issue so its history is imported, or run `estigia doctor` to see the store; do not act on a guess. |
| `store-unwritable` | The local store's directory sits on a filesystem reached over a network, whose locking and WAL cannot be trusted to keep the store consistent. The connection is not opened, so nothing was read from the tracker and nothing was written. | Point `HOME` at a local filesystem, or move `~/.estigia` off the network mount, and call again. |
| `expected-epoch-moved` | `--expected-epoch` named an epoch, or `none`, and the newest publication on the branch's own pull request is another. The refusal carries `expected_epoch` and `recorded_epoch`. The check runs after the timeline read and before the draft conversion and the push: nothing was pushed and no pull request was touched. Stale class. | The answer you acted on is out of date. Read the state again and decide from the epoch it now names; do not repeat the call with the recorded epoch unseen. |
| `published-transaction-missing` / `published-transaction-mismatch` | Either a caller-supplied epoch/PR/head/base/digest is incomplete or is not the latest recorded publication, or an operation that names no receipt at all (`review_read` (`view: findings`), `republish_review`) found the issue has no complete publication to read or force against. | For a supplied receipt, use the latest complete one, or republish and review the new epoch. For an issue with no recorded publication, publish the review target first — there is nothing to answer, lease, or force against yet. |
| `published-transaction-unparseable` | A `published` marker on the timeline carries one or more of its receipt fields (`epoch`, `pr`, `head`, `base`, `digest`) present but unreadable — a missing field, a value that does not parse, or one of the wrong width. Reading it as though no publication existed would be the nearest named state; the refusal carries the marker's `epoch` and the first offending `field`. | Read that `published` comment on the tracker and repair or remove it. Nothing was pushed and no pull request was touched. |
| `correction-state-unparseable` | A `published` marker carries at least one of its correction-budget fields (`budget-genesis-tree`, `budget-genesis-paths`, `budget-original-lines`, `budget`, `budget-cumulative`) present but unreadable. Read as absent, a half-written budget would reset the lineage's cumulative to zero and hand the next repair a fresh allowance in silence; the refusal carries the marker's `epoch` and the first offending `field`. A marker carrying *none* of the budget fields is the legitimate pre-budget migration path and is never refused. | Read that `published` comment on the tracker and repair or remove it. Nothing was pushed and no pull request was touched. |
| `review-handoff-requester-excluded` / `reviewer-not-distinct` | The publishing/requesting run tried to acquire its own unresolved handoff, or to be credited with reviewing its own receipt. | Use another run, or credit the reviewer you actually acquired. Time, CI and prose never discharge it. |
| `recorded-by-capture-only` | A lens report, a refutation or a validator result was recorded by hand, or `record_review_finding` named a `lens`. Only `collect_review_input` records these, after the binary ran the reviewer. Nothing was written. | Call `review_status` for the slot it offers, then `launch_review_input` and then `collect_review_input` with that slot's name. |
| `qualifying-review-verdict-missing` | The newest full receipt on its own pull request is not cleared by a computed verdict: it is not `low`, and it has no lens report and no recorded computed verdict. A `review-verdict` `accepted` verdict clears nothing. | Keep the PR draft and the issue in `review`; read `review_status` for the lens slots still unrecorded and call `launch_review_input` and then `collect_review_input` for each, then `record_computed_verdict`. A lens report cannot be recorded by hand: a hand-recorded lens report is refused `recorded-by-capture-only`. When no reviewer CLI can run (`reviewer-cli-missing`), call `handoff_review` so a run that has `claude` or `codex` on `PATH` takes the review. A deleted comment reaches here too — evidence that is gone is evidence that is missing. |
| `legacy-verdict-rejected` | A distinct reviewer recorded a `rejected` `review-verdict` against these exact bytes. The marker binds its receipt, at every tier, whatever the ledger computes. | Keep the PR draft; correct the change and `republish_review`: the new receipt starts without it. |
| `rejected-on-insufficient-evidence` | A distinct reviewer's `rejected` `review-verdict` stands over these exact bytes and a severe finding that reviewer recorded against the receipt declares `insufficient` — the word that says neither demonstration nor inference established it. A rejection may not rest on a finding that declares it established nothing. | Keep the PR draft. Record that observation as a `warning` or a `suggestion`, informational and never a rejection, or establish it and declare `deterministic` or `inferential`, then `republish_review` and review the new receipt. |
| `review-verdict-retired` | An aggregate verdict was recorded. The aggregate verdict is retired: no reviewer records a verdict, and the verdict is computed from the receipt's ledger. Nothing was written. | Call `launch_review_input` and then `collect_review_input` for every lens slot `review_status` offers, then `record_computed_verdict` for the exact receipt. |
| `review-receipt-escalated` | The transaction's terminal receipt is `escalated`: the decision passed to a named person, and an escalation does not substitute for an approved computed verdict, whatever the ledger computes. | Keep the PR draft; the named person decides. Only an approved computed verdict recorded by a run that is neither the publisher nor a requester supersedes the escalation. |
| `escalate-review-correction-unspent` | `escalate_review` was called while `review_status`'s `corrections` do **not** answer `correction_spent`. The escalation records the exit a spent correction forces, so it is refused while the lineage still has a correction left. | Publish the correction, or record the computed verdict. Read `review_status` first and escalate only when its `corrections` answer `correction_spent`. |
| recover-is-for-a-person | An agent's shell line runs `estigia recover`, a maintainer's command. The gate denies it on every host, with no claim needed, and does not ask. | Tell the person the exact command and let them run it in their own shell, or with `!` in Claude Code; never run it. |
| `recover-not-a-maintainer` / `recover-permission-unreadable` | GitHub says the named login holds neither the `admin` nor the `maintain` role (the refusal names the role and permission it holds), or GitHub did not answer the read — an unanswered question is never a maintainer. | A maintainer names their own login; for an unreadable answer, check the login and the token's access and run it again. |
| `blank-recover-reason` / `recover-epoch-unknown` | `estigia recover` was given no reason, or an epoch no publication on this issue carries. | State the reason, and name an epoch `review_read` with `view: transaction` reports. |
| `recovery-record-missing` | A publication carries a recovered-from field and no readable local recovery record matches its parent, so the tier and lens focus it must keep are unknown. | Restore the local store, or publish the work as a new change on a new pull request. |
| `recover-receipt-not-escalated` | The receipt does not stand escalated — a computed `escalated` verdict, or a local `escalated` receipt no distinct approval superseded. A stale receipt is refused earlier, as `published-transaction-mismatch`. | Correct a rejected receipt, release an approved one, review an unjudged one. |
| `invalid-recover-login` | `--authorized-by` is blank or is not a GitHub login. | Name the login. |
| `recover-no-escalated-receipt` / `recover-epoch-ambiguous` | The short form (`--epoch` omitted) found no receipt on the issue that stands escalated and is not yet recovered, or found several (the refusal lists them). | Nothing to recover in the first case; in the second, name the receipt with `--epoch`. |
| `recover-login-unresolved` | The short form (`--authorized-by` omitted) could not read the login `gh` is authenticated as. | Name the maintainer's login with `--authorized-by`. |
| `escalate-review-already-approved` | The transaction already carries an `approved` receipt, and an escalation cannot overwrite it. An approval is final; the escalation would shadow the approved computed verdict and make `release_ci` refuse `review-receipt-escalated`. | Release CI on the computed verdict, or republish the change as a fresh transaction if a person's decision is genuinely owed. Do not re-send the escalation. |
| `invalid-escalate-target` / `blank-escalate-reason` | `--escalated-to` was empty or whitespace-only — an escalation addressed to nobody is not a decision anybody owns — or `--reason` was empty, whitespace-only or filler. | Name the person who takes the decision, and state the condition the decision is handed over with. |
| `release-pr-mismatch` / `release-target-mismatch` | The current draft PR or freshly derived clean target differs from the receipt. | Do not release CI; republish and obtain fresh review evidence. |
| `ready-readback-failed` | The ready write was not confirmed with the same PR/head/base. | Re-read the PR before any further action; the write outcome is not established. |
| `publication-lane-forbidden` | This token may not start workflows, so `publish_review` could not dispatch the publication lane. The branch is pushed and **no receipt was recorded**. | Grant the permission — `gh auth refresh -s workflow`, or `actions: write` on the token in `GH_TOKEN` — then run the same call again; it reuses the pull request. |
| `publication-readback-disagrees` | The branch was pushed and the pull request exists, but readback never confirmed the expected head, base and draft. | `publication-unconfirmed` | The newest complete publication on the receipt's own pull request carries `unconfirmed=true` — the push landed, the PR readback never confirmed it — so review, handoff, verdict and CI cannot bind to that receipt. | Run `republish_review` after correcting the cause; it leases against that head and records a confirmed receipt. Do not hand force-push. |
| `invalid-refutation-batch` | A refutation batch's `outcomes` did not parse as a JSON array of `{"id", "outcome"}` objects, or an entry named no `id`. | Supply a JSON array of `{"id": <finding id>, "outcome": <corroborated\|refuted\|inconclusive>}` objects. |

They exist because the operations are answered **in process** now rather than by a command line: an
argument the caller left out used to be `argparse`'s refusal on the way in, and something has to say
it here. What must never happen is the alternative — an operation nobody implements answered with
`ok`, or handed somewhere unnamed and coming back looking answered.
